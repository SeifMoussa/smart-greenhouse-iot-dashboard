# Data Model

The backend uses SQLAlchemy 2 ORM with SQLite. Four tables; no foreign keys; tiny by design.

The source of truth for the schema is [`backend/src/greenhouse/models.py`](../backend/src/greenhouse/models.py).

---

## Conventions

- **All timestamps are naive UTC.** The Pydantic schema layer normalises any incoming tz-aware timestamps to naive UTC before they reach the ORM. Outgoing values are serialised as ISO 8601 without a timezone suffix; clients should treat them as UTC.
- **Enums are enforced at the Pydantic boundary**, not at the database level. SQLite is permissive about strings, so the validation happens before the row is built. The set of allowed values:
  - `sensor.type` ∈ `{temperature, humidity, soil_moisture, light}`
  - `actuator.id` ∈ `{fan, pump, light}`
  - `actuator.state` ∈ `{on, off}`
  - `alert.severity` ∈ `{warning, critical}`
- **No foreign keys.** Each table stands alone. Joins between `readings`, `alerts`, and `thresholds` happen by `type` string at query time. This is intentional: alerts are denormalised (they carry their own copy of the threshold band that was in effect at the moment of breach) so retrospective threshold edits never change history.

## Tables

### `readings`

One row per ingested sensor reading.

| Column | Type | Constraints | Index | Notes |
|---|---|---|---|---|
| `id` | INTEGER | PK, autoincrement |  | Surrogate identity |
| `sensor_id` | VARCHAR(64) | NOT NULL | ✓ | Caller-provided device identifier (e.g. `esp32-01`, `esp32-sim-01`) |
| `type` | VARCHAR(32) | NOT NULL | ✓ | One of the four sensor literals |
| `value` | FLOAT | NOT NULL |  |  |
| `unit` | VARCHAR(16) | NOT NULL |  | e.g. `C`, `%`, `lux`; not normalised against the type |
| `timestamp` | DATETIME (naive) | NOT NULL, default `utc_now()` | ✓ | When the reading was observed |
| `created_at` | DATETIME (naive) | NOT NULL, default `utc_now()` |  | When the backend persisted the row |

**Composite index:** `ix_readings_type_timestamp(type, timestamp)` — supports the "last N of type X" query that powers the live tiles and the history chart.

---

### `thresholds`

One row per sensor type. Defaults are seeded on first start.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `type` | VARCHAR(32) | **PK** | Sensor type literal; one of `temperature`, `humidity`, `soil_moisture`, `light` |
| `min_value` | FLOAT | NOT NULL |  |
| `max_value` | FLOAT | NOT NULL | Must be strictly greater than `min_value` (enforced at Pydantic, not at DB) |
| `updated_at` | DATETIME (naive) | NOT NULL, default and `onupdate` to `utc_now()` |  |

**Seeded defaults** (see `db.py:DEFAULT_THRESHOLDS`):

| Type | Min | Max |
|---|---|---|
| `temperature` | 15.0 | 32.0 (°C) |
| `humidity` | 40.0 | 80.0 (%) |
| `soil_moisture` | 30.0 | 80.0 (%) |
| `light` | 200.0 | 1500.0 (lux) |

The seed step is idempotent — it only inserts rows that don't already exist, so restarting an initialised DB is a no-op.

---

### `alerts`

One row per detected threshold breach. Generated by the ingest path inside the `POST /api/readings` route — no separate "alert producer".

| Column | Type | Constraints | Index | Notes |
|---|---|---|---|---|
| `id` | INTEGER | PK, autoincrement |  |  |
| `type` | VARCHAR(32) | NOT NULL | ✓ |  |
| `value` | FLOAT | NOT NULL |  | The reading value that triggered the alert |
| `threshold_min` | FLOAT | NOT NULL |  | Snapshot of the band at the time of breach |
| `threshold_max` | FLOAT | NOT NULL |  | Snapshot of the band at the time of breach |
| `severity` | VARCHAR(16) | NOT NULL |  | `warning` or `critical` |
| `message` | VARCHAR(255) | NOT NULL |  | Human-readable description (`Value 35.0 is above maximum 32.0`) |
| `created_at` | DATETIME (naive) | NOT NULL, default `utc_now()` | ✓ |  |

**Severity rule** (see `thresholds.py:evaluate`):

```
distance = how far past the band the value is
band_width = max - min  (clamped to a safety floor of 1.0)
critical when distance / band_width > 0.25
warning  otherwise
```

So the same reading can be a warning today and a critical tomorrow if you tighten the band — but **historical alerts retain the threshold values that were active when they were created**, because the alert row carries its own snapshot of `threshold_min` / `threshold_max`.

---

### `actuator_state`

One row per actuator. The complete set is seeded on first start.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | VARCHAR(32) | **PK** | One of `fan`, `pump`, `light` |
| `name` | VARCHAR(64) | NOT NULL | Display label (`Ventilation Fan`, `Water Pump`, `Grow Light`) |
| `state` | VARCHAR(8) | NOT NULL | `on` or `off` |
| `updated_at` | DATETIME (naive) | NOT NULL, default and `onupdate` to `utc_now()` |  |

**Seeded defaults** (see `db.py:DEFAULT_ACTUATORS`):

| ID | Name | Initial state |
|---|---|---|
| `fan` | Ventilation Fan | `off` |
| `pump` | Water Pump | `off` |
| `light` | Grow Light | `off` |

## Relationships

There are no foreign keys. The conceptual relationships are:

```
readings.type  ──┐
                 ├──▶ thresholds.type  (PK)
alerts.type    ──┘

(actuator_state stands alone)
```

Why no foreign keys?

- The set of sensor types is fixed and short (four literals). Enforcing it in the schema layer (Pydantic `Literal`) is more expressive and gives a 422 with a clear error before any DB call happens.
- Alerts carry their own snapshot of the threshold band, so they don't need a live join.
- SQLite's foreign-key enforcement is off by default unless `PRAGMA foreign_keys=ON` is set per connection — quietly skipping a constraint is worse than not declaring one.

## Timestamp handling

Three places handle timestamps; the conventions are:

1. **Backend storage.** `models.py:utc_now()` returns `datetime.now(timezone.utc).replace(tzinfo=None)` — naive UTC. All `DateTime` columns default to this.
2. **Incoming requests.** `schemas.py:_normalize_to_naive_utc` converts any tz-aware datetime to naive UTC before it reaches the route handler. Future timestamps are rejected if more than 5 minutes ahead (clock-skew tolerance).
3. **Outgoing responses.** Pydantic v2 serialises naive `datetime` as ISO 8601 without a `Z` suffix. Clients should interpret as UTC. The frontend's `formatRelative` and `formatTime` helpers parse with `new Date()` which treats trailing-suffix-less strings as local time — that's a known small UX wart on dashboards loaded outside UTC. For the lab demo it's acceptable; production code would either prepend `Z` on serialisation or use `Date.UTC()` parsing.

## Retention / future improvements

This is a single-tenant demo, so retention is intentionally absent. Practical next steps when scaling beyond the lab:

- **Time-partitioning.** Move `readings` and `alerts` into monthly partitions (or use a time-series store like TimescaleDB / InfluxDB).
- **TTL on readings.** A nightly task that deletes readings older than N days. The dashboard only ever queries the last 7 days at the longest range.
- **Alert deduplication.** Currently every breach generates a new alert. A "first-fire" / "still-firing" pattern with hysteresis would cut noise.
- **Auditable actuator log.** Right now `actuator_state` only carries the current state. A separate `actuator_events` table would record every transition.
- **Foreign keys + migrations.** Move from auto-`create_all` to Alembic migrations and turn on `PRAGMA foreign_keys=ON` (or migrate to Postgres).
- **Per-device telemetry.** `readings.sensor_id` is currently free-form. A `devices` table with last-seen / metadata would help once multiple ESP32 nodes exist.

These are deliberately out of scope for the portfolio demo — listed here so a reviewer can see I know what the next mile looks like.
